# Pengui Slides — Functional Specification

**Version:** 2.0 (Print Mode addition)
**Status:** Draft
**Purpose:** Add a second, equally first-class output medium to Pengui Slides — printable PDF documents (A4 / US Letter portrait) — suitable for exam study summaries, handouts, whitepapers, and any print-oriented content. Print mode shares the Design Soul system, asset pipeline, validation engine, and MCP App editor shell with the existing slide presentation mode. Nothing about existing slide behavior changes.

**v2.0 changes over v1.x:**

- **Format primitive at the deck level.** Every deck now declares a `format`: the existing `slides_16_9` (default, unchanged behavior) or one of the new `print_a4_portrait` / `print_letter_portrait` formats.
- **Geometry-sensitive code paths parameterized.** Renderer viewport, validator safe-area checks, overflow detection, and PDF exporter page size all read from `deck.format` instead of global 1920×1080 constants.
- **Print-context recipe family.** 10 new HTML recipe templates under `templates/print/` covering cover, TOC, chapter intro, content+chart, content+diagram, compare, glossary, timeline, summary, bibliography.
- **First-class diagram & chart system.** Inline-SVG recipes with soul-token styling; the tree / mind-map diagram is the flagship primitive, matching the horizontal hierarchy + pastel categories + orthogonal connectors style used in real study materials. Charts (bar, line, pie) are SVG-generated by the LLM following documented recipes.
- **Print-mode typography overrides.** Soul token generator emits a smaller body-type scale and more generous leading when approving a soul intended for print use.
- **Optional page-chrome slot.** A `<!-- @page-chrome ... -->` directive allows decks to opt into page numbers and a running title at export time. Cross-page state (numbering, references) resolves during PDF assembly, not per-slide.
- **MCP App redesign.** Aligned with the Cozy Premium design system from the sibling `study-audio-mcp` project. Svelte 5 `$state` runes, route-based shell, shared `tokens.css` / `motion.css` / primitives (Sidebar, Toast, Card, Button, Tabs). The editor canvas adapts to the deck's format; print decks get a vertical scrollable multi-page preview.
- **Export scope.** Print decks are **PDF-only**. `export_pptx` and `export_google_slides` detect print-format decks and return a typed error pointing to `export_pdf`. Google Slides is out of scope for print mode.

---

## 1. Overview

Pengui Slides v2.0 generalizes from "slide deck generator" to "HTML-first document generator" by introducing a `Format` concept at the deck level. The core pipeline is unchanged:

```
User Brief → LLM generates HTML/CSS → Validator checks soul compliance + geometry → Playwright renders → Exporter assembles PDF/PPTX
```

What's new is that "1920×1080" is no longer hardcoded; it's one row in a `FORMAT_REGISTRY`. Two rows exist today:

| Format                 | Width × Height (px) | Orientation | Safe Area | Exporter surface           |
|------------------------|---------------------|-------------|-----------|----------------------------|
| `slides_16_9`          | 1920 × 1080         | landscape   | 48px      | PPTX, PDF, HTML, GSlides   |
| `print_a4_portrait`    | 1240 × 1754         | portrait    | 96px      | PDF                        |
| `print_letter_portrait`| 1275 × 1650         | portrait    | 96px      | PDF                        |

Both mediums share:

- Design Souls (color, typography, spacing, shape, depth, components, motion tokens)
- Token-only CSS enforcement (literal hex/px values are rejected by the validator)
- Asset system (`asset://UUID` references resolved at render time)
- Two-stage validation (static lint ≈50ms + render-truth ≈800ms)
- Revision tracking
- MCP App live-preview editor with text-edit commits

What differs is:

- Page geometry (width, height, safe area inset) — threaded from `deck.format`
- Default typography scale (print is smaller)
- Recipe library (slide recipes vs. print recipes)
- Exporter surface (print is PDF-only)
- MCP App canvas aspect and preview layout

Net-new capabilities for print mode:

1. Print-aware recipes that leverage vertical space and body-text density.
2. Inline-SVG diagram family (tree/mind-map + chart types) that the LLM generates following documented templates, with soul tokens flowing through automatically.
3. Page-chrome slot protocol for running headers and page numbers.

## 3. The Format Primitive

### 3.1 Types

```ts
// src/types/format.ts

export type FormatKind =
  | 'slides_16_9'
  | 'print_a4_portrait'
  | 'print_letter_portrait';

export type FormatMedium = 'slides' | 'print';

export interface FormatGeometry {
  /** Internal canvas width in pixels (at 1× scale). */
  widthPx: number;
  /** Internal canvas height in pixels. */
  heightPx: number;
  /** Safe-area inset in pixels (uniform). */
  safeAreaInsetPx: number;
  /** Target DPI for PDF export. Informational; PDF export uses page.pdf() with CSS @page size in px. */
  dpi: number;
  /** Orientation hint for the MCP App and export metadata. */
  orientation: 'landscape' | 'portrait';
  /** Medium category — drives exporter availability and default recipe library. */
  medium: FormatMedium;
  /** Physical page label for print PDFs ('A4', 'Letter'), null for screen formats. */
  physicalPage: 'A4' | 'Letter' | null;
  /** Default thumbnail aspect for the MCP App canvas (width/height). */
  thumbnailAspect: number;
}

export interface Format {
  kind: FormatKind;
  geometry: FormatGeometry;
}
```

### 3.2 Registry

```ts
// src/domain/formats/format-registry.ts

export const FORMAT_REGISTRY: Record<FormatKind, Format> = {
  slides_16_9: {
    kind: 'slides_16_9',
    geometry: {
      widthPx: 1920, heightPx: 1080, safeAreaInsetPx: 48,
      dpi: 96, orientation: 'landscape', medium: 'slides',
      physicalPage: null, thumbnailAspect: 16 / 9,
    },
  },
  print_a4_portrait: {
    kind: 'print_a4_portrait',
    geometry: {
      widthPx: 1240, heightPx: 1754, safeAreaInsetPx: 96,
      dpi: 150, orientation: 'portrait', medium: 'print',
      physicalPage: 'A4', thumbnailAspect: 1240 / 1754,
    },
  },
  print_letter_portrait: {
    kind: 'print_letter_portrait',
    geometry: {
      widthPx: 1275, heightPx: 1650, safeAreaInsetPx: 96,
      dpi: 150, orientation: 'portrait', medium: 'print',
      physicalPage: 'Letter', thumbnailAspect: 1275 / 1650,
    },
  },
};

export const DEFAULT_FORMAT: FormatKind = 'slides_16_9';
```

**Why these pixel dimensions for print?**

A4 physical is 210×297mm = 8.27×11.69in. At 150 DPI this is 1240×1754 px. 150 DPI is the sweet spot for (a) crisp text in the rendered PDF, (b) reasonable rendering time (2× the surface area of a 16:9 slide vs. 4× at 300 DPI), and (c) a pixel count that still renders cleanly at display resolution in the MCP App preview. The PDF exporter uses `page.pdf()` with `format: 'A4'` directly so the output carries proper vector geometry regardless of the internal pixel raster; the 1240×1754 figure is an internal canvas size, not a physical constant.

Similarly, US Letter (8.5×11in) at 150 DPI = 1275×1650 px. Safe-area inset of 96px ≈ 15mm at 150 DPI, a standard print margin.

### 3.3 Deck integration

`Deck` gains an optional `format?: FormatKind` field. When absent (legacy decks), the deck-service treats it as `slides_16_9`. `CreateDeckInput` adds an optional `format` parameter to `create_deck`; omission preserves the pre-v2.0 default.

`DeckSummary` now includes `format: FormatKind` so the MCP App and tool consumers can branch UI/behavior without re-fetching the deck.

### 3.4 Threading through the pipeline

Every site that previously assumed 1920×1080 now reads the deck's format. Concrete call sites:

| File                                                         | What changes                                                                         |
|--------------------------------------------------------------|--------------------------------------------------------------------------------------|
| `src/domain/rendering/slide-renderer.ts`                     | Viewport size derived from `format.geometry` (already accepts width/height options). |
| `src/domain/rendering/preview-renderer.ts`                   | Thumbnail aspect derived from `format.geometry.thumbnailAspect`.                     |
| `src/domain/rendering/pdf-exporter.ts`                       | Replaces `SLIDE_WIDTH/HEIGHT` consts with passed-in geometry; `page.pdf()` uses physical page for print. |
| `src/domain/rendering/pptx-exporter.ts`                      | Unchanged for slides; rejects print decks at the tool layer (see §6).                |
| `src/domain/validation/stage1/safe-area-check.ts`            | Expected width/height/inset derived from a geometry argument.                        |
| `src/domain/validation/stage2/overflow-detector.ts`          | `SLIDE_WIDTH/HEIGHT` constants replaced with per-check geometry.                     |
| `src/domain/souls/recipe-generator.ts`                       | Emits print recipes when soul is approved in a print context.                        |
| `src/tools/decks/create-deck.tool.ts`                        | New `format` param.                                                                  |
| `src/tools/export/export-pdf.tool.ts`                        | Passes deck format into the exporter.                                                |
| `src/tools/export/export-pptx.tool.ts`                       | Refuses print decks with typed error.                                                |
| `src/tools/export/export-google-slides.tool.ts`              | Refuses print decks with typed error.                                                |
| `src/tools/export/render-preview.tool.ts`                    | Thumbnails sized from deck format.                                                   |
| `app/src/**`                                                 | Canvas aspect, preview layout, export panel all format-aware.                        |

Validator signatures change from `run(html, soulTokenNames, allowedFonts)` to `run(html, soulTokenNames, allowedFonts, geometry: FormatGeometry)`. Call sites in `stage1-runner.ts` and `stage2-runner.ts` are updated to pass the deck's geometry down. All existing slide tests continue to pass because the default format resolves to the same 1920×1080 numbers.

## 4. Slide HTML Contract

The per-slide HTML contract is unchanged in structure. What changes is that the `.slide` root container's declared `width`/`height` and padding now must match the deck's format geometry (still via token reference):

```html
<!DOCTYPE html>
<html>
<head>
  <style>
    :root {
      --color-canvas: #FAF7F2;
      /* ... all soul tokens ... */
      --page-width: 1240px;   /* from deck.format.geometry.widthPx */
      --page-height: 1754px;  /* from deck.format.geometry.heightPx */
    }
    .slide {
      width: var(--page-width);
      height: var(--page-height);
      padding: var(--space-safe-area);
      overflow: hidden;
    }
  </style>
</head>
<body>
  <!-- @slide-meta {"title":"...","type":"cover","narrative":"...","tags":[]} -->
  <div class="slide">
    <!-- Content -->
  </div>
</body>
</html>
```

**Rules unchanged:**
- No external network dependencies (no CDN fonts, no remote scripts).
- No JavaScript required for layout.
- Fixed root container at the deck's format dimensions with the deck's safe-area inset.
- All visual values via CSS custom properties — literal hex/px rejected.
- `<!-- @slide-meta {...} -->` comment required.

**New for print mode:**
- The `@slide-meta` `type` field may take print-specific values: `cover`, `toc`, `chapter_intro`, `content`, `content_chart`, `content_diagram`, `compare`, `glossary`, `timeline`, `summary`, `bibliography`.
- An optional `<!-- @page-chrome {...} --> ` directive opts the page into running headers / page numbers. See §7.

## 5. Design Souls and Print Mode

### 5.1 Typography overrides

Soul approval generates CSS custom properties for typography: `--text-display`, `--text-h1`, `--text-h2`, `--text-body`, `--text-caption`, etc. For slides, body defaults to 24–32px. For print, the same logical scale maps to smaller physical sizes suitable for A4 reading distance:

| Token             | Slide default | Print default |
|-------------------|---------------|---------------|
| `--text-display`  | 96px          | 56px          |
| `--text-h1`       | 72px          | 36px          |
| `--text-h2`       | 48px          | 24px          |
| `--text-h3`       | 36px          | 18px          |
| `--text-body`     | 28px          | 12px          |
| `--text-caption`  | 20px          | 9px           |
| `--leading-body`  | 1.4           | 1.55          |

Souls don't fork. The same soul definition is used; the token generator emits two CSS blocks conditionally, keyed by format medium. Souls always ship both so a deck can change format without needing re-approval.

### 5.2 Spacing

`--space-*` tokens retain their soul-defined logical meanings. `--space-safe-area` resolves to the format's safe-area inset (48px for slides, 96px for A4/Letter print).

### 5.3 Recipe library

A soul's recipe library is format-aware. Approving a soul generates both:

- **Slide recipes** (6, unchanged): title slide, two-column, metrics, features grid, closing CTA, blank themed.
- **Print recipes** (10, new): cover, TOC, chapter intro, content, content + chart, content + diagram, compare (two-column), glossary, timeline, summary, bibliography.

Recipes are plain HTML with token-only CSS. The LLM uses them as starting points, not rigid templates.

## 6. Tools

The tool surface gains backward-compatible parameters and two typed error rows. No existing tool is removed.

### 6.1 `create_deck`

New optional `format` parameter. Default remains `slides_16_9`.

```ts
inputSchema: z.object({
  soul_id: z.string(),
  title: z.string().nullish(),
  author: z.string().nullish(),
  format: z.enum(['slides_16_9', 'print_a4_portrait', 'print_letter_portrait']).nullish()
    .describe('Output format. Defaults to slides_16_9 (16:9 presentation).'),
})
```

Output adds a `format: FormatKind` field.

### 6.2 `export_pdf`

Unchanged surface. Internally reads `deck.format` and uses the format's physical page when present. For print formats, `mode` defaults to `direct` (vector text, smaller files, sharper typography); for slide formats it remains `image`.

### 6.3 `export_pptx`

Detects print-format decks and returns:

```json
{
  "error": "format_not_exportable",
  "message": "Print decks cannot be exported as PPTX. Use export_pdf instead.",
  "deck_format": "print_a4_portrait",
  "suggested_tool": "export_pdf"
}
```

### 6.4 `export_google_slides`

Same behavior as `export_pptx` — typed error for print decks. Google Slides remains unsupported for print.

### 6.5 `export_html`

Exports a print deck as a single scrollable HTML document with CSS `@page` breaks. Useful for web previews and browser-based print-to-PDF. Slide decks retain the existing behavior (keyboard navigation between slides).

### 6.6 `render_preview`

Thumbnail dimensions derived from the deck's `thumbnailAspect`. For print decks, thumbnails are 192×272 (≈A4 portrait at a glance); for slides, 480×270 (current).

### 6.7 Soul tools

`approve_design_soul` gains the print-mode recipe generation described in §5.3. No input change.

### 6.8 MCP App tools

`open_deck_editor` is format-aware: the editor reads `deck.format` from the editor state and lays out its canvas / page rail accordingly. No tool signature change.

## 7. Page Chrome (Headers, Footers, Page Numbers)

Print decks opt into running page chrome via a directive placed alongside `@slide-meta`:

```html
<!-- @page-chrome {"runningTitle": "Inorganic Cosmetics — Minerals", "pageNumber": true, "footerAlign": "right"} -->
```

Fields:

| Field          | Type    | Default      | Meaning                                                      |
|----------------|---------|--------------|--------------------------------------------------------------|
| `runningTitle` | string  | deck.title   | Text rendered in the header strip.                           |
| `pageNumber`   | bool    | `true`       | Whether to render "Page X of Y" in the footer.               |
| `footerAlign`  | enum    | `'right'`    | `'left' \| 'center' \| 'right'`                              |
| `hide`         | bool    | `false`      | Suppress chrome on this specific page (e.g., cover / TOC).   |

**Resolution happens at export time**, not per-slide. The PDF exporter assembles a composite HTML document with `@page` margin boxes populated from the directive, and Playwright's `page.pdf({ displayHeaderFooter, headerTemplate, footerTemplate })` does the rendering. The templates are generated from the deck's soul tokens so chrome color, typography, and spacing stay consistent. Cross-page state (total page count, page numbering) resolves during assembly — slide HTML does not know its own page number.

Per-slide validation ignores the `@page-chrome` comment beyond a syntactic JSON check.

## 8. Diagram & Chart System

### 8.1 Approach

LLM generates inline SVG, styled entirely with soul tokens. No runtime chart library, no Python rendering, no external images. This keeps:

- Full color/typography control via the soul
- Vector-sharp output in PDF direct mode
- Zero external dependencies
- LLM creativity within constrained templates

The MCP resource `pengui://docs/charts-and-diagrams` ships comprehensive templates with working SVG that the LLM adapts to its data.

### 8.2 Tree / Mind-Map Diagram (flagship)

Matches the reference style: horizontal root → categories (colored groups) → leaf nodes with subtitles, connected by orthogonal right-angle paths. Example use: "Minerals → Pigments/Absorbents/Texturizers → specific compounds."

Template structure:

```
<svg viewBox="0 0 1040 760" ...>
  <!-- Connectors (drawn first, behind nodes) -->
  <path d="M120,380 H200 V120 H280" class="connector" />
  ...
  <!-- Root node -->
  <g transform="translate(40,360)">
    <rect class="node node-root" rx="14" .../>
    <text class="node-title">Minerales</text>
    <text class="node-subtitle">10 materias primas</text>
  </g>
  <!-- Category nodes, colored by category -->
  <g transform="translate(280,80)">
    <rect class="node node-category category-pigments" rx="14" .../>
    ...
  </g>
  <!-- Leaf nodes -->
  <g transform="translate(560,40)">
    <rect class="node node-leaf category-pigments" rx="10" .../>
    ...
  </g>
</svg>
```

Soul tokens drive:

- Node fill (`--color-category-a/b/c/d` derived from soul accent family + tints)
- Node border (`--color-border`, `--border-width-medium`)
- Node radius (`--radius-sm`, `--radius-md`)
- Title/subtitle typography (`--text-h3`, `--text-caption`, `--leading-body`)
- Connector stroke (`--color-border-strong`, `stroke-width: 1.5`)

### 8.3 Chart types

Documented in the same resource, with minimal SVG templates:

- **Bar chart (vertical / horizontal)** — axes, labels, value labels on bars, category colors.
- **Line chart** — grid, axes, data polyline, point markers, legend.
- **Pie chart** — slices with percentage labels, legend, inner stroke for separation.
- **Comparison matrix** — styled HTML table (not SVG) with soul-token borders.
- **Timeline (horizontal)** — labeled events along an axis with category coloring.

### 8.4 Validator rule

Stage 1 adds an opt-in `diagram-legibility` check that triggers on slides whose metadata type is `content_diagram` or `content_chart`:

- SVG must declare a `viewBox`.
- All text elements must set `font-size` via `var(--text-*)` tokens (no literals).
- Node/bar/slice fills must be soul tokens (no literal hex).
- If a chart has more than 1 series, a legend element must be present (`<g class="legend">`).

The rule fires warnings, not errors — it's guidance, not a gate.

## 10. MCP App (Editor)

### 10.1 Design direction

The existing `DeckEditorApp.svelte` is a single 1000-line file with inline styles. v2.0 rebuilds it around the **Cozy Premium** design system from `study-audio-mcp`:

- `app/src/styles/tokens.css` — warm neutrals, mint accent, radius/shadow/motion tokens
- `app/src/styles/globals.css` — typography, resets, focus rings
- `app/src/styles/motion.css` — easing/duration variables, canonical transitions
- `app/src/lib/primitives/` — `Sidebar.svelte`, `Toast.svelte`, `Card.svelte`, `Button.svelte`, `Tabs.svelte`, `Chip.svelte`
- Svelte 5 `$state` runes throughout
- Route-based layout with a `route` state variable and a `Sidebar` for navigation

Stated design feel (from `study-audio-mcp/design_style.md`):

> Cozy-premium. Morning light on paper. Calm confidence, soft tactility, quiet delight. Clarity over chrome, warmth over sterility, spacing over lines.

### 10.2 Routes

| Route    | Purpose                                                                 |
|----------|-------------------------------------------------------------------------|
| `decks`  | Library of all decks with format badges, last-modified, thumbnail cover |
| `editor` | The current single-slide editor, canvas adapts to deck format           |
| `export` | Live PDF preview with one-click download, soul picker, format info      |

### 10.3 Editor canvas

- For `slides_16_9`, unchanged: 16:9 canvas with thumbnail rail.
- For print formats: portrait canvas. Thumbnail rail uses `thumbnailAspect`. Below the active page, a **multi-page vertical preview** scrollable stack shows all pages at reduced scale for continuous-reading context. Page numbers in the gutter.

### 10.4 Export panel

- Detects deck format. For slide decks, shows PPTX / PDF / HTML / Google Slides buttons. For print decks, shows PDF with optional mode toggle (direct default) and a live preview iframe rendering the composite HTML with page-chrome. Download button triggers `export_pdf` and offers the result as a download link (using the `sidecar_paths` / `file_path` from the tool response).

### 10.5 Statelessness

Defer the full stateless redesign to a later iteration. The new app reads from tool results (matching v1.x), but the architecture separates a thin client state layer (`stores/`) from server-derived state (`lib/bridge.ts` loaders) so a future stateless migration is a lower-friction change.

- Existing decks without a `format` field resolve to `slides_16_9` at read time.

## 14. Non-goals (v2.0)

- **Flowing pagination.** Print content is authored as discrete pages, one HTML document per page, same as slides. True HTML → paginated-flow is out of scope; the LLM takes responsibility for splitting content across pages.
- **Auto-generated TOC / index.** The LLM authors the TOC page from its own outline. No automated cross-page link resolution.
- **Bleed / crop marks / professional print prep.** Out of scope. Print mode targets personal / study / handout use.
- **Google Slides for print.** Explicitly declined by the owner.
- **Editable PDF forms.** Out of scope.
- **Footnote auto-numbering across pages.** Out of scope.
